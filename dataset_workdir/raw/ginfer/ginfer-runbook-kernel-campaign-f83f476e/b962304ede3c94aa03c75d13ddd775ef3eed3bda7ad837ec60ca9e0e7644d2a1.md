# Agentic kernel optimization campaign

This is the repository-local runbook for sustained handwritten CUDA optimization. It supplements
the Op ownership and qualification rules in [`op-development.md`](op-development.md); it does not
change an Op's numerical contract or make a microbenchmark an inference result.

## Campaign record

Freeze these facts before the first build:

| Field | Required value |
|---|---|
| Target order | model routes in the order assigned by the user |
| Host | hostname, GPU SKU, compute capability, driver, CUDA compiler |
| Accepted start | full commit ID shared by local, origin, and the campaign host |
| Artifact | exact path, registered identity, size, and hash when practical |
| Workload | mode, draft width, KV format/capacity, graph/prefix state, context, concurrency |
| Correctness | independent Op oracle, dispatch seams, Engine semantic fixtures, registered real test |
| Performance | public-Op matrix and named target Program/public Engine boundary |
| Controls | candidates per cycle, acceptance threshold, and no-win terminal count |

The active campaign convention is 24 candidates per cycle. The first candidate that clears every
gate closes the cycle, becomes the accepted baseline, and starts a new cycle with a fresh profile.
A target stops after one complete 24-candidate cycle produces no accepted candidate. The user may
replace any of these values; record the replacement in the campaign result before continuing.

The active real-boundary gate is two independent candidate repetitions, each at least 2% faster
than the fresh cycle baseline, with exact accounting and no material regression at unaffected
concurrency points or route seams. A hypothesis-specific public-Op gate may be stronger when the
kernel's measured share shows that a smaller Op gain cannot produce a 2% round win.

## Worktree and build preparation

The primary checkout on every host is read-only during a campaign. The published optimization
line is `perf/agentic-kernels`; each machine checks it out in a dedicated worktree:

```text
<ginfer-repository>/.worktrees/agentic-kernels/
├── build-86/       one Release sm_86 image for RTX 3090
├── build-89/       one Release sm_89 image for RTX 4090
├── build-120a/     one Release sm_120a image for 5090 or PRO 6000
└── profiles/
    ├── sm86/rtx3090/<target>/<cycle>/
    ├── sm89/rtx4090/<target>/<cycle>/
    └── sm120a/<sku>/<target>/<cycle>/
```

The branch isolates history; the worktree isolates source, CMake state, generated objects, and
profiles. Do not build in or switch the primary checkout, reuse a CMake cache from another
worktree/SM, or copy selected source files into an ad-hoc optimization directory.

For an existing campaign worktree:

1. inspect the primary repository and dedicated worktree with read-only Git commands;
2. require the campaign worktree to be clean and on `perf/agentic-kernels`;
3. fetch origin and advance only by fast-forward;
4. verify its full HEAD equals origin and the coordinating checkout;
5. query the live GPU/toolchain and confirm the artifact and fixtures; and
6. configure or validate the Release build cache for exactly the native architecture.

For a missing worktree, create `<repo>/.worktrees/agentic-kernels` from the fetched branch without
changing the primary checkout. Never use `reset --hard`, force checkout/push, automatic stash,
merge, or rebase to manufacture synchronization. Stop on dirty state or divergent history.

On Server 2, first discover and verify the current repository rather than assuming the historical
path. The required native tree is `build-86`, and campaign evidence belongs under
`profiles/sm86/rtx3090/`. Run Muse Glimmer before Qwen3.8-27B unless the user changes the order.

## Candidate accounting and commits

A candidate is one falsifiable implementation mechanism. It consumes a slot when its first source
edit begins, even if it fails compilation, correctness, or an early performance gate. A mechanical
repair remains the same candidate; a different mechanism, resource policy, or dispatch domain is
a new one. Baseline collection, read-only profiling, and retained benchmark enabling work do not
consume a slot.

Record the diagnosis before editing: measured bottleneck, decisive evidence, proposed mechanism,
expected affected and neutral points, and the observation that rejects it. Then use this gate order:

1. focused compile;
2. independent numerical/exact oracle at affected shapes and dispatch seams;
3. affected public-Op matrix and production-weighted extent;
4. target Program round, including a repeat of the decisive point;
5. unaffected concurrency points and route seams; and
6. short- and long-context public Engine semantic sentinels plus the registered real test.

Reject as soon as a lower gate disproves the hypothesis. Generated text must be coherent and pass
the fixture's independent retrieval/task oracle, but plausible output never replaces an Op oracle.
For stochastic generation, retain prompt/output token counts and acceptance accounting; do not
present different trajectories as a strict paired kernel comparison.

Commit each remotely executed candidate. Reject through a normal revert commit and append a ledger
row with the candidate/commit, mechanism, prediction, oracle result, public-Op result,
real-boundary result, decision, and restoration commit. This keeps the accepted source clean while
preserving why a tempting idea was rejected.

## Cycle closure and evidence

After an accepted candidate:

1. retain its source and legitimate public benchmark/test changes;
2. push and verify the exact commit on every participating worktree;
3. close the cycle ledger with the paired matrix and semantic results; and
4. collect a fresh baseline/profile before the next candidate cycle.

After a complete no-win cycle, restore the accepted source through normal reverts, verify the final
source matches the cycle-start source, rebuild/retest the accepted binary, commit the result and
concise rejection ledger, and apply the terminal rule. Then freeze a new target-specific baseline
for the next model in the declared sequence.

Commit accepted source, retained tests/benchmarks, the campaign controls, summarized results, and
concise ledgers. Large `.nsys-rep`/Nsight Compute reports, SQLite exports, full model logs, and build
products stay in the ignored host-specific profile/build tree. The result document records their
location and enough provenance to interpret the summarized claims.

Before handoff, require a clean synchronized branch, no source snapshots or forced selectors,
passing focused oracle and registered real test, a committed result/ledger, and explicit pending
physical-GPU qualification.
