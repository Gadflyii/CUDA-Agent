# Architecture Notes: `sm_86`, `sm_89`, and `sm_120a`

Read this reference when adding architecture-specific code, changing launch/resource policy, or
interpreting results across the campaign. These are compile-time facts and design prompts, not a
substitute for querying the live device and profiling the exact binary.

## Resource envelope

| Exact image | Family in this campaign | Max resident warps/SM | Max blocks/SM | 32-bit registers/SM | Shared memory/SM | Max shared memory/block |
|---|---|---:|---:|---:|---:|---:|
| `sm_86` | Ampere / RTX 3090 | 48 | 16 | 64K | 100 KB | 99 KB |
| `sm_89` | Ada / RTX 4090 | 48 | 24 | 64K | 100 KB | 99 KB |
| `sm_120a` | Blackwell / RTX 5090 and RTX PRO 6000 | 48 | 32 | 64K | 128 KB | 99 KB |

CUDA reserves part of the per-SM shared-memory capacity, and static shared-memory allocations have
additional limits. Query the device/function attributes and use the required opt-in before relying
on large dynamic allocations. Resource ceilings do not predict the best launch by themselves.

## `sm_86`: Ampere client path

- Compile explicitly for `86`; the tuning guide notes architecture-specific FP32 throughput that a
  generic `sm_80` image does not fully target.
- Hardware-accelerated global-to-shared asynchronous copy, split arrive/wait barriers, and native
  warp-wide 32-bit integer reductions are available design options.
- The lower 16-block/SM ceiling can expose block-count or shared/register limits sooner than on
  Ada or Blackwell. Measure block residency and grid waves rather than copying an Ada tile.
- Do not route FP8- or Blackwell-only formats/instructions here. Preserve an intentional Ampere
  implementation or explicit admission rejection according to the GInfer contract.

## `sm_89`: Ada client path

- Compile explicitly for `89`. Ada retains the 48-warp and 100 KB shared-memory envelope of
  compute capability 8.6 but raises the block limit to 24.
- Ada adds fourth-generation Tensor Cores with FP8 support. That does not make every FP8 or small-M
  path Tensor-Core efficient; measure packing, padding, and epilogue overhead.
- AD102 has a much larger L2 than GA102, so a route may show materially different reuse even when
  the kernel source is shared. Treat 4090 results as Ada evidence, not Ampere evidence.
- Ampere-style asynchronous copy remains a candidate where staged reuse justifies it.

## `sm_120a`: architecture-specific Blackwell path

- Build the exact architecture-specific `120a` image for features whose PTX support requires
  `sm_120a`; do not assume a generic or different Blackwell-family target admits the same
  instructions.
- Compute capability 12.0 has 48 resident warps, 32 blocks, 128 KB shared memory per SM, and 99 KB
  maximum shared memory per block according to the current tuning guide.
- Thread-block clusters and distributed shared memory are available, but cluster size and
  occupancy must be computed with the cluster occupancy APIs. Cluster communication is not free;
  keep accesses coalesced and compare against an L2/global-memory design.
- Blackwell-specific Tensor Core, low-precision, TMA, or PTX routes require exact toolchain/header
  support, compile guards, a semantic fallback or explicit route restriction, and physical
  qualification.
- The RTX 5090 and RTX PRO 6000 share `sm_120a` but not SKU-level SM count, memory system, power
  behavior, or performance. Never combine their timing distributions.

## Dispatch and qualification rules

- Compile-time instruction eligibility comes from the exact CUDA architecture target and toolkit;
  runtime policy comes from capability/geometry/device attributes. Never dispatch by marketing
  name.
- A newer family is not proof that a technique is faster. Keep family-specific tile/block/stage
  constants when measured crossovers justify them.
- Compile all images for a shared source change. Run public correctness and the same workload
  matrix on physical `sm_86`, `sm_89`, and both `sm_120a` SKUs before making a campaign-wide claim.
- Requery live SM count, memory, driver, compiler, and resource attributes in every report. The
  table above should guide source design, not hard-code a launch policy.
